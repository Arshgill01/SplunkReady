## Findings

### HIGH-001: Rule results are not bound to the rule being evaluated
- Severity: High
- File: `src/grader/engine.ts:117`
- Evidence: `runRuleEngine` parses `rule.id` and `rule.severity`, then returns `rule.evaluate(context)` without validating that the returned `RuleEvaluation.ruleId` or `RuleEvaluation.severity` matches the rule that was just run. The public `fail(ruleId, violations)` helper can be called with any `GraderRuleId`, and each violation is only parsed with `violationSchema`; it is not checked against the enclosing rule id. The current tests in `tests/grader/engine.test.ts` cover only matching rule/result ids.
- Why it matters: Wave 22 is the deterministic rule-engine foundation. If a rule declared as `SPL-001` can emit a `KO-001` result or violation, the engine can preserve array order while losing the provenance that later receipts need to cite exact deterministic checks. It also makes severity less explainable because the declared rule severity and emitted result severity can diverge.
- Required fix: In `runRuleEngine`, enforce the rule boundary after evaluation: `result.ruleId` must equal `rule.id`, `result.severity` must equal the canonical severity for that rule, `rule.severity` should match the canonical `ruleSeverityById[rule.id]`, and every emitted violation should have `violation.ruleId === rule.id` plus the canonical severity. Add negative tests that a mismatched result id/severity and mismatched violation id/severity are rejected.
