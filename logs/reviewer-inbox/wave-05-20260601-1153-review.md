## Findings

### HIGH-001: Runtime schemas accept write/destructive Splunk tools
- Severity: High
- File: `src/schemas/core.ts:53`, `src/schemas/core.ts:89`
- Evidence: `environmentContractSchema` validates `mcpTools` with unrestricted `stringListSchema`, and `missionSchema` validates both `expectedTools` and `allowedTools` with unrestricted `stringListSchema`. The Wave 04 source contract says `mcpTools` are read-only Splunk MCP tools and that `mcpTools` must not include write or destructive Splunk operations (`docs/schemas/core-contracts.md:34`, `docs/schemas/core-contracts.md:50`). It also says a mission cannot authorize Splunk mutation (`docs/schemas/core-contracts.md:111`). Current tests cover deterministic checks, invalid trace fields, missing `traceRefs`, and restricted indexes, but there is no negative test proving mutation-capable tools are rejected.
- Why it matters: SplunkReady's hard boundary is that the app must not auto-mutate Splunk. If Wave 05 establishes runtime validators that accept arbitrary tool names, later fixture/live adapter work can compile or run a mission that authorizes mutation without failing validation. That weakens both fixture/live parity and demo honesty because safety would depend on later call-site discipline instead of the contract.
- Required fix: Add a shared read-only Splunk MCP tool allowlist or explicit mutation-tool rejection predicate and apply it to `EnvironmentContract.mcpTools`, `Mission.expectedTools`, and `Mission.allowedTools`. Add negative tests for at least one mutation-capable or destructive tool name in the environment contract and mission allowlist.
