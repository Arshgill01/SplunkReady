## Findings

### HIGH-001: Mission check badges are still not scoped to mission-specific violation evidence
- Severity: High
- File: `src/ui/shell.ts`
- Evidence: Unresolved. `renderMissionCheckBadges` still builds `beforeRuleIds` and `afterRuleIds` from every violation passed into the mission table using only `violation.ruleId`. `renderMissionList` still calls it for each mission row with the same unfiltered `beforeViolations` and `afterViolations` collections. The diff in `tests/ui/shell.test.ts` still covers only one mission, so it does not prove that violations from one mission cannot affect another mission row that declares the same check id.
- Why it matters: Wave 75 adds a visible evidence claim to the UI. If the badge status is not mission-scoped, the shell can claim a deterministic check is failed or resolved for a mission without mission-specific violation evidence.
- Required fix: Filter violations by `mission.id` before deriving check badges, or pass already mission-scoped violation sets to the badge renderer. Add a negative multi-mission test where two missions share a check id but only one mission has the violation; the unaffected mission must not show that check as failed or resolved.
