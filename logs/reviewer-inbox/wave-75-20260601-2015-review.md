### HIGH-001: Mission check badges are not scoped to mission-specific violation evidence
- Severity: High
- File: `src/ui/shell.ts`
- Evidence: `renderMissionCheckBadges` builds global `beforeRuleIds` and `afterRuleIds` from all violations by `ruleId` only at `src/ui/shell.ts:475` and `src/ui/shell.ts:476`. `renderMissionList` then applies that same global rule-id set to every mission row at `src/ui/shell.ts:501` through `src/ui/shell.ts:506`. This means a `SPL-001` violation for one mission would mark `SPL-001` as failed or resolved for every mission that declares the same check, even if that mission has no such violation. The focused test at `tests/ui/shell.test.ts:357` through `tests/ui/shell.test.ts:377` covers only a single mission, so it cannot catch cross-mission leakage.
- Why it matters: The Wave 75 acceptance criterion says deterministic-check status must be backed by real before/after violation evidence. Mission rows are claim surfaces in the demo UI; cross-mission leakage would make the UI overclaim evidence and weaken receipt provenance.
- Required fix: Filter before/after violations by the current mission id before deriving check status, or otherwise pass mission-scoped violation sets into the badge renderer. Add a negative test with two missions that share a check id where only one mission has the violation, proving the unaffected mission is not marked failed or resolved.
